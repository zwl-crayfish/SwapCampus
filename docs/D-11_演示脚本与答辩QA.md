### Slide 3 — 项目背景（40秒）

> 为什么做这个项目？校园闲置交易基本都在微信群和朋友圈，每天两百多条消息，但信息散乱、搜不到、价格靠猜、交易完了也没有信用记录。
>
> 所以我们想做一个完整的平台：买家可以搜索、浏览、收藏、下单、聊天；卖家可以发布、管理、上下架；管理员可以审核内容、处理举报。目标是覆盖从发布到交易完成再到信用积累的完整闭环。
>
> 我们明确不做在线支付和资金托管——原因很简单，校园里大家本来就要见面交易，线上支付反而增加资质门槛和开发复杂度。

---

### Slide 4 — 需求亮点（30秒）

> 核心场景三条：卖家发布多图商品、买家检索下单聊天、双方确认完成交易形成信用记录。
>
> 关键约束：学号唯一标识身份、订单需要买卖双方都确认才算完成、举报处罚和商品状态在一个事务里同步、搜索排序用 SQL 白名单防注入、JWT 无状态认证配合 Redis 黑名单实现退出登录。

---

### Slide 5 — 系统架构（1分钟）

> 整体是前后端分离的分层架构。前端 Vue 3 SPA + Element Plus + Pinia 状态管理，通过 Nginx 反向代理到后端。后端 Spring Boot 3.2，MyBatis-Plus 做持久层，Spring Security + JWT 做无状态认证，WebSocket 用 STOMP 协议实现实时聊天。
>
> 基础设施选 MySQL 8、Redis 7 缓存、MinIO 存储商品图片。全栈通过 Docker Compose 编排，五个容器一个桥接网络，一份 .env 文件管理密钥。

---

### Slide 6 — 数据库设计（40秒）

> 10 张表围绕用户、商品、订单三条主线：user 是核心，学号和用户名都设了唯一约束；goods 用 UUID 做外部标识，status 字段驱动状态流转；orders 记录买卖双方，通过 buyer_confirm 和 seller_confirm 两个字段实现双确认机制。
>
> 外键维持引用完整性，InnoDB 事务保证跨表一致。关键索引包括商品标题的全文索引、收藏的联合唯一索引、消息的时间排序索引。

---

### Slide 7~8 — 关键模块实现（1分钟）

> 挑两个核心模块讲。注册流程：校验学号和用户名唯一 → BCrypt 加密密码 → 写入 user 表 → JWT 签发，同一事务提交。
>
> 订单流程更复杂：校验商品在售且不是自己发布的 → 创建订单同步置商品为已售 → 买家卖家分别确认 → 首次双方确认后交易完成，自动给双方加信用分。任一方取消则恢复商品上架。
>
> 举报治理也很关键：一次处理同步更新举报状态、下架商品、扣减信用分、记录处理人和时间，全部在一个事务内提交。

---

### Slide 9 — 关键算法（30秒）

> 说两个技术选型。商品搜索我们在 SQL 层用 MyBatis `<choose>` 标签限定排序字段只能是 `created_at` 或 `price`，避免拼接 SQL 注入。
>
> 订单确认用状态机：0 待确认 → 买家或卖家单方确认后状态不变 → 双方都确认后进入 2 已完成。通过检查对方确认状态实现锁定，避免重复触发信用结算。

### Slide 16 — 遇到的最大挑战（1分钟）

> 讲两个印象最深的。

> 第一个，分支合并引发全链路回退。我们合并了一个历史分支，结果 application.yml 从 MySQL 被替换成 H2 内存库，Dockerfile 多阶段构建退化成单阶段，docker-compose 里环境变量全变成硬编码，CI 连 Docker 构建任务都丢了。注册、部署、CI 三线同时崩溃。
> 我们逐文件 diff 对比合并前后差异，一个文件一个文件恢复。同时保留了那个分支带来的 202 条种子商品数据，最后形成了 H2 本地开发 + MySQL 生产部署的双 profile 架构——坏事变好事。

> 第二个，CI 流水线连续 10 多次失败。每次修好一个错误，下一个才暴露出来。先是 mvnw 没执行权限，修好后又报 Maven 参数缺失，修好后数据库报 Table "users" not found，再修好又报 actuator 接口 403。
> 我们对着原始日志一层层往下挖，定位到文件权限模式、Maven Wrapper 参数完整性、实体注解和硬编码 SQL 的一致性、SecurityConfig 白名单这四个根因，拆成小 PR 逐个合并，最终 CI 全绿通过。

## 预设 Q&A

### 架构 & 技术选型

**Q1：为什么用单体而不用微服务？**
> 五人团队、两周开发周期，微服务会增加服务间通信、分布式事务、独立部署的复杂度。分层单体在本项目规模下足够，代码组织清晰、事务管理简单、部署只需要一个 JAR。架构上我们通过接口层—业务层—持久层的清晰分层预留了未来拆分能力。

**Q2：为什么选 MyBatis-Plus 而不是 JPA？**
> 我们有多条件动态搜索需求——关键词、分类、排序字段组合变化——MyBatis 的动态 SQL 对这种场景更灵活。JPA 的 Specification 也可以做，但复杂查询可读性不如 SQL。

**Q3：WebSocket 的安全性怎么保证？**
> 目前 `/ws` 端点允许匿名连接，在生产版本中需要补 JWT 拦截——在 STOMP CONNECT 阶段校验 Token。当前通过 Spring Security 保护消息发送的 REST 端点。

---

### 数据库 & 事务

**Q4：注册和钱包为什么不在一个事务里？**
> 这是设计上的取舍。当前注册只写 user 表，钱包在 DataInitializer 里为种子数据初始化，新用户注册时尚未创建钱包。如果要补齐，应该在 AuthService.register() 上加 @Transactional，同时写入 User 和 Wallet。

**Q5：订单双确认如果一方不确认怎么办？**
> 目前通过 cancelOrder 接口允许任一方取消订单，商品自动恢复上架。未来可以加超时自动取消机制——下单 24 小时内未完成确认则自动取消。

**Q6：信用分机制怎么设计的？**
> 初始 80 分，完成交易双方各 +2 分（上限 100），被举报核实后 -10 分（下限 0）。信用分影响买家下单信心和卖家商品展示权重——目前权重未实现，是预留扩展点。

---

### CI/CD & 部署

**Q7：CI 目前没有实际测试代码，怎么保证质量？**
> 后端 `./mvnw test` 目前无测试用例执行，CI 主要保证编译通过和依赖正确。测试代码是后续演进的重点——至少应补齐 GoodsService 和 OrderService 的单元测试。

**Q8：K8s 和 Docker Compose 区别是什么？**
> Docker Compose 适合单机开发和演示，一键启动所有服务。K8s 是生产环境方案，支持多副本、滚动更新、健康检查自动重启、水平扩容。我们两套都有完整配置。

**Q9：为什么不直接用云服务？**
> 课设场景下需要完整展示自建能力。如果上线运营，MySQL 可以迁云 RDS、MinIO 可换 S3/OSS、Redis 用云服务，迁移成本低——配置都是环境变量注入的。

---

### 业务 & 需求

**Q10：线下交易怎么防止虚假商品或欺诈？**
> 三层：学号实名注册确保可追溯、信用分评价机制形成信誉约束、举报系统 + 管理员审核做平台治理。不支持在线支付反而避免了资金诈骗——本来就依托校园信任关系。

**Q11：和闲鱼有什么区别？为什么不直接用闲鱼？**
> 闲鱼是公域流量，买卖双方跨城市，依赖物流和在线支付。校园交易是熟人半熟人场景，面交更方便、不需要物流、信任成本低。我们做了校园特有的双确认机制和信用分体系，比闲鱼更贴合校园使用习惯。

**Q12：为什么不接学校的统一认证？**
> 这是需求分析阶段和老师讨论后确定的边界——统一认证需要协调信息中心，课设周期内不具备对接条件。我们设计了学号唯一约束预留接口，后续可以替换为 OAuth/LDAP 认证。

---

### 项目管理 & AI 使用

**Q13：五个人怎么分工不打架？**
> 接口设计阶段先冻结 API 契约（返回格式、字段名、路径），然后前后端并行开发。每人建 feature 分支，CI 检查通过后才能合并。合并冲突最多的是配置文件，通过代码 Review 解决。

**Q14：AI 写了多少代码？**
> AI 辅助了文档结构、模板代码生成、CI 错误诊断。所有业务逻辑——特别是事务边界、状态流转、SQL 白名单——都是我们自己设计实现的。AI 输出的内容我们逐条对照源码验证过。

---

### 总结

**Q15：如果重做一次，你会改什么？**
> 三件事：第一，从第一天就写好测试——现在的代码没有测试覆盖，后面补的代价大得多。第二，数据库表名一开始就统一——我们遇到过 `user` vs `users` 的不一致问题。第三，加一个 Flyway 做数据库版本迁移，而不是手动执行 SQL 脚本。
