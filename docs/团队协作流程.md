## 一、前置准备（每位成员只需配置一次）

### 1.1 安装 Git

```bash
# macOS
brew install git

# Windows
# 下载: https://git-scm.com/download/win
```

### 1.2 配置 Git 用户信息

```bash
git config --global user.name "你的姓名"
git config --global user.email "你的邮箱@bjfu.edu.cn"
```

### 1.3 生成 SSH Key 并添加到 GitHub

```bash
# 1. 生成密钥（一路回车即可）
ssh-keygen -t rsa -b 4096 -C "你的邮箱@bjfu.edu.cn"

# 2. 复制公钥
cat ~/.ssh/id_rsa.pub
```

3. 打开 https://github.com/settings/keys → **New SSH key**
4. 粘贴公钥内容 → 保存

### 1.4 配置 SSH 代理（国内用户需要）

由于 Clash 代理会拦截 SSH 流量，GitHub SSH 需要单独配置走代理：

```bash
cat >> ~/.ssh/config << 'EOF'
Host github.com
    HostName github.com
    User git
    Port 22
    ProxyCommand nc -X 5 -x 127.0.0.1:7897 %h %p
EOF
```

> 如果 `nc` 命令报错，尝试：`brew install netcat` 或改用 `ProxyCommand ssh -q -W %h:%p 127.0.0.1`

### 1.5 配置 Git HTTP 代理（可选，用于 HTTPS 方式 clone）

```bash
git config --global http.proxy http://127.0.0.1:7897
git config --global https.proxy http://127.0.0.1:7897
```

### 1.6 克隆项目

```bash
git clone git@github.com:zwl-crayfish/SwapCampus.git
cd SwapCampus
```

## 三、日常开发流程

### 3.1 完整流程

```
成员领任务
    │
    ▼
从 main 创建 feature 分支
    │
    ▼
写代码 → 本地测试通过
    │
    ▼
提交并推送到 GitHub
    │
    ▼
创建 Pull Request
    │
    ├── CI 自动构建检查 ←── 失败 → 修复后重新push
    │
    ▼
组员 Code Review
    │
    ▼
✅ 全部通过 → 合并到 main → 删除分支
```

### 3.2 操作步骤

```bash
# ── 第1步：每天开始工作前，同步最新代码 ──
git checkout main
git pull origin main

# ── 第2步：从 main 创建任务分支 ──
git checkout -b feature/你的功能名

# ── 第3步：写代码...写代码...写代码... ──

# ── 第4步：提交改动 ──
git add .
git commit -m "feat: 完成了xxx功能"

# ── 第5步：推送到 GitHub ──
git push origin feature/你的功能名

# ── 第6步：浏览器打开 GitHub，创建 Pull Request ──
# https://github.com/zwl-crayfish/SwapCampus
# 页面会自动提示你刚刚推送的分支，点击"Compare & pull request"
# 填写 PR 描述 → 点击 "Create pull request"

# ── 第7步：等待 CI 和 Review ──
# CI 自动运行（约1-2分钟）
# 在群里通知组员 Review
```

### 3.3 分支命名规范

| 前缀 | 用途 | 示例 |
|------|------|------|
| `feature/` | 新功能开发 | `feature/user-login` |
| `fix/` | Bug 修复 | `fix/goods-image-upload` |
| `docs/` | 文档修改 | `docs/srs-section3` |
| `refactor/` | 代码重构 | `refactor/order-service` |
| `chore/` | 构建/CI/配置 | `chore/add-dockerfile` |

## 四、CI/CD 自动化

### 4.1 触发时机

| 事件 | 行为 |
|------|------|
| 创建 PR 到 `main` | 🔄 自动运行 CI |
| 推送新 commit 到已有 PR | 🔄 自动重新运行 |
| 合并 PR 到 `main` | 🔄 最终验证 |

### 4.2 CI 做什么

```
          Pull Request
              │
    ┌─────────┴─────────┐
    ▼                   ▼
┌──────────┐      ┌──────────┐
│ Backend  │      │ Frontend │
│ Build    │      │ Build    │
├──────────┤      ├──────────┤
│启动MySQL │      │ npm ci   │
│建表      │      │ npm run  │
│Maven编译 │      │ build    │
│运行测试  │      │          │
└──────────┘      └──────────┘
    │                   │
    └─────────┬─────────┘
              ▼
       ┌──────┴──────┐
       │  全部通过？   │
       ├──────┬──────┤
       ▼      ▼      │
      ✅     ❌      │
      可合并  需修复  │
       │      │      │
       │  修改代码    │
       │  重新push   │
       │      │      │
       └──────┘      │
```

### 4.3 CI 失败怎么办

PR 页面会显示具体错误，常见情况及修复：

```
❌ Backend Build & Test — Failed
   GoodsController.java:45 缺少分号
   → 改完后: git add . && git commit -m "fix" && git push

❌ Frontend Build — Failed
   Chat.vue: 'stompClient' is not defined
   → 修复导入语句后重新push

❌ 数据库连接失败 — 通常是 CI 环境偶发，点 "Re-run jobs"
```

修改后 push 到同分支，CI 自动重跑，**不需要关闭 PR 重新创建**。

## 五、Code Review 规范

### 5.1 谁来 Review

- **至少 1 人 Review 并 Approve** 后才能合并
- 组长必须 Review 所有 PR
- 建议对应模块的负责人也参与 Review

### 5.2 怎么 Review

1. 打开 PR 页面 → **Files changed** 标签
2. 逐行查看代码改动
3. 发现问题：鼠标悬停在行号上 → 点蓝色 ➕ → 写评论
4. 全部看完后 → 右上角 **Review changes** 绿色按钮
5. 选择 **Approve** ✅ → 提交

### 5.3 Review 关注什么

- [ ] 代码逻辑是否正确？
- [ ] 命名是否清晰？
- [ ] 是否有遗留的调试代码（console.log, system.out）？
- [ ] 是否影响了其他模块？
- [ ] 相关文档是否同步更新？

### 5.4 合并 PR

Review 通过 + CI 全部 ✅ 后：

1. PR 页面 → **Merge pull request** → **Confirm merge**
2. 合并后 **删除远程分支**（GitHub 会自动提示）

```bash
# 合并后，本地也同步清理
git checkout main
git pull origin main
git branch -d feature/已完成的分支名  # 删除本地分支
```

## 八、常见问题

### Q1: push 的时候提示 "Permission denied"

SSH key 没有配置或没有添加到 GitHub。参考 [1.3 节](#13-生成-ssh-key-并添加到-github) 重新配置。

### Q2: git pull 时出现冲突

```bash
# 1. 先保存本地改动
git stash

# 2. 拉取最新代码
git pull origin main

# 3. 恢复本地改动
git stash pop

# 4. 如果有冲突，手动解决冲突文件
#    删除 <<<<<<  ====== >>>>>> 标记，保留正确代码

# 5. 标记冲突已解决并提交
git add .
git commit -m "merge: 解决与main的冲突"
```

### Q3: CI 运行失败但本地没问题

- 检查是否忘记提交新文件（`git status` 确认）
- 检查代码是否依赖本地环境的特定配置
- 在 PR 页面点击 "Re-run jobs" 重试
- 如果持续失败，在 PR 评论区 @ 组长

### Q4: 不小心在 main 分支上改了代码

```bash
# 1. 保存改动到临时分支
git checkout -b feature/temp-fix
git add .
git commit -m "temp: 暂存改动"

# 2. 切回main并撤销改动
git checkout main
git reset --hard origin/main

# 3. 在临时分支上继续工作
git checkout feature/temp-fix
# 根据任务重命名分支: git branch -m feature/正确的名字
```

### Q5: 合并后需要清理远程分支吗？

GitHub 在 PR 合并后会自动提示 **"Delete branch"**，点击即可删除远程分支。这样仓库不会堆积大量已合并的历史分支。

## 九、检查清单（每次提交前）

- [ ] 我是从最新的 `main` 创建的分支吗？
- [ ] 我的代码能在本地正常运行吗？
- [ ] 提交信息是否清晰地描述了改动？
- [ ] 有没有留下调试代码（console.log, System.out）？
- [ ] 相关的文档需要更新吗？
- [ ] 分支名是否符合命名规范？
